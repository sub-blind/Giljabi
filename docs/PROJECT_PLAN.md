# StoryRoute 개정 기획서

2026년 9월 17일 · 1인 개발 · Next.js 기반 React 프런트엔드 + FastAPI 백엔드

이 문서는 기존 통합 제안서와 29개 화면 시안을 수정한 개발 기획이다. 구현 완료나 공모전 제출 완료를 의미하지 않는다. 실제 제공 기능은 개발 결과를 기준으로 공식 기능설명서에 옮긴다.

지역 기준은 강원특별자치도 전체다. 현재 전체 검색·18개 시군 선택과 관광사진·오디·연관 관광지 화면 연결을 구현했다. 실제 검증과 미완료 항목은 [검증 기록](VALIDATION.md), 데이터 판단은 [강원도 API 선정안](API_SELECTION_GANGWON.md)을 따른다.

## 1. 서비스 소개

**원하는 조건으로 강원도의 실제 장소를 고르고, 자동차 이동을 확인한 뒤 여행 중에도 코스를 이어 쓰는 반응형 웹 서비스.**

서비스명은 StoryRoute를 유지한다. 지역 범위는 강원도 전체다. 시군을 좁혀 당일 코스를 구성하도록 안내한다. 주변 반경 검색은 후속 확장이다. 사용자는 최대 세 곳을 선택하고, 장소를 바꾸거나 순서를 수정해 자신의 코스를 완성한다. 후보가 적거나 짧은 여행을 원하는 경우 한두 곳으로도 완성할 수 있다.

## 2. 해결할 문제와 사용 이유

사용자는 장소 검색, 조건 비교, 지도 확인을 반복하면서 여행 계획을 만든다. AI가 결과를 제시하더라도 어떤 조건을 이해했는지, 장소를 왜 골랐는지 알기 어렵고 수정하려면 다시 질문해야 한다.

StoryRoute는 조건 해석을 사용자에게 보여주고 수정하게 한다. 추천된 장소는 카드에서 직접 고르고 바꿀 수 있으며, 실제 관광 정보와 방문 순서를 함께 확인할 수 있다. 목표는 검색 시작부터 짧은 코스 완성까지의 과정을 줄이는 것이다.

차별성은 광범위한 경쟁 서비스에 대한 우월성 주장 대신 아래 행동으로 설명한다.

- **해석을 고친다:** AI가 추출한 조건을 확인하고 수정한 뒤 검색한다.
- **장소를 바꾼다:** 현재 실제 조회된 후보 안에서 다른 장소를 골라 코스를 조정한다.
- **이유를 확인한다:** 관광 데이터에서 확인한 정보와 AI 설명을 구분한다.

이것이 한 번의 여행 계획 흐름 안에서 작동하도록 만든다.

## 3. 대표 시나리오

사용자: “강원도에서 바다도 보고 식사도 하는 하루 여행을 하고 싶어.”

1. 서비스가 관심 조건을 해석한다. 지역은 강원도, 기간은 당일로 표시하고 시군을 직접 고르거나 후보 장소에서 시작할 수 있게 한다.
2. 사용자는 관심 유형·키워드 등을 수정한다.
3. FastAPI가 지원하는 관광 검색 조건으로 변환해 실제 장소를 조회한다.
4. 사용자는 후보 카드에서 최대 세 곳을 고른다.
5. 마음에 들지 않는 곳은 다른 후보로 바꾼다.
6. 방문 순서를 바꾸고 ‘자동차 이동 확인’으로 장소 사이 예상 시간·거리·도로 경로를 조회한다. 첫 장소로 가거나 직전 코스 장소에서 다음 장소로 가는 카카오맵 길찾기를 연다.
7. 코스를 이 브라우저에 저장하거나 ‘여행 시작’을 누른다.
8. 다음 미방문 장소를 확인하고 직접 방문 체크와 장소별 메모를 남긴다. 저장한 코스를 다시 열면 해당 코스의 기록을 복원한다.

처음에는 ‘조건으로 찾기’를 보여주며, 사용자가 ‘문장으로 찾기’ 또는 ‘사진으로 찾기’로 바꿀 수 있다. LLM 접근이 없으면 문장 해석 준비 중임을 알리고 직접 조건 선택으로 연결한다. 해석 실패도 표시하며 실제 관광 검색은 계속 사용할 수 있다.

## 4. 첫 버전 기능

| 기능 | 완료 기준 |
|---|---|
| 여행 조건 입력 | 문장·예시 선택 또는 직접 조건 선택으로 검색 가능 |
| AI 조건 해석·수정 | 고정된 출력 형식, 사용자 수정 우선, 실패 시 직접 선택 가능 |
| 실제 장소 검색 | TourAPI 조회 결과의 사진·분류·주소·누락 상태 표시 |
| 장소 선택·교체 | 최대 세 곳 선택, 중복 방지, 현재 후보에서 대안 제안 |
| 하루 코스 확인 | 선택 장소의 순서 변경, 방문 순서 마커·점선, 자동차 이동 확인·도로 경로, 구간별 외부 길찾기 |
| 여행 실행·기록 | 여행 시작, 다음 미방문 장소, 직접 방문 체크, 장소별 500자 메모·복원 |
| 추천 근거 | 확인한 필드와 조회 정보에 근거한 AI 설명 표시 |
| 브라우저 저장 | 장소 ID·순서·조건만 저장하고 다시 열 때 실제 정보 재조회 |
| 관광사진 탐색 | 촬영지에서 강원도 확인, 해당 지역 실제 관광 후보 검색 |
| 장소 이야기 | 관광지명·제공 좌표를 대조한 오디 원본 대본·오디오 |
| 연관 장소 | 기준월 표시, 국문 관광정보에서도 이름·지역을 확인한 후보만 연결 |
| 방문 편의정보 | 무장애 서비스의 동일 장소 확인 후 제공 항목만 표시, 빈 항목을 불가로 단정하지 않음 |

‘다른 장소 뽑기’는 실제 조회한 후보 범위에서 수행하는 추첨이다. 전국 장소 전체의 균등 추첨이나 학습 기반 추천으로 표현하지 않는다. 대체 후보가 없으면 검색 조건 변경을 안내한다.

## 5. 사용자 화면

### 여행 만들기

하나의 검색 영역에서 ‘조건으로 찾기’, ‘문장으로 찾기’, ‘사진으로 찾기’ 세 탭 중 하나만 보여준다. 처음에는 ‘조건으로 찾기’가 열린다. 탭을 바꿔도 입력한 문장과 편집한 조건은 유지한다. 오른쪽에 별도 안내 영역을 두거나 사진 검색 폼을 항상 펼쳐 두지 않는다.

조건 탭에서는 지역과 장소 유형을 먼저 고른다. 선호 키워드는 필요할 때 펼쳐 입력한다. 문장 탭에서는 여행 문장과 예시를 제공하며, 명시적인 해석 버튼을 눌렀을 때만 요청한다. 해석에 성공하면 같은 검색 영역의 조건 탭으로 전환하고 편집 영역에 초점을 옮겨 결과를 확인·수정하게 한다. AI 연결이 준비되지 않았으면 준비 중 안내와 직접 조건 선택 버튼을 보여준다.

사진 탭은 사용자가 조회 버튼을 눌렀을 때만 관광사진 API를 호출한다. 다른 탭으로 이동해도 사진 화면은 숨김 상태로 유지하여 입력한 필터와 조회 결과를 보존한다. 지역 바로가기는 검색 영역 아래에 짧은 행으로 배치하며 실제 시군 장소 검색으로 연결한다.

제목과 촬영지가 같은 사진은 한 카드 안에서 넘겨 본다. 로드에 실패한 사진은 제외하고 작은 안내를 표시하며, 해당 카드에 남은 사진이 없으면 카드를 숨긴다. 사진은 원본 비율을 유지해 전체를 보여주고 현재 사진의 촬영자와 출처를 함께 표시한다.

### 장소 고르기

사진 중심 카드, 확인된 기본 정보, 장소 상세 패널, 선택 목록과 다음 단계 버튼으로 구성한다. LLM 설명을 기다리느라 후보 카드 표시를 지연시키지 않는다. 카드의 근거는 우선 지역·분류·검색 키워드 등 확인된 정보로 표시한다.

### 내 하루 코스

방문 순서, 장소 교체·삭제·순서 변경, 추천 설명, 지도 마커·방문 순서 점선, 구간별 카카오맵 길찾기와 브라우저 저장으로 구성한다. 여행 시작 후 다음 미방문 장소를 표시하고 방문 체크·장소별 메모를 남긴다. 방문 체크는 사용자가 직접 남긴 기록이며 위치 인증이 아니다. 고정된 방문 시각이나 확인하지 않은 이동 분 수는 표시하지 않는다. 자동차 이동 확인을 누르면 실제 API 응답의 예상 시간·거리와 도로 경로 실선을 표시한다. 순서를 바꾸면 이전 경로를 숨기고 다시 확인하게 한다. 조회 전의 점선은 방문 순서로 구분한다.

조건 편집과 상세정보는 별도의 페이지가 아닌 패널로 제공한다. 로딩·오류·빈 결과·후보 부족은 각 화면 안에서 처리한다. 관광사진은 입력 화면에서 명시적으로 조회하고, 오디·연관 자료는 상세의 버튼을 누를 때 조회한다. 추가 API 실패가 기본 검색을 막지 않는다. 연관 자료는 2025년 4월을 기본 기준월로 사용하며 현재 인기나 실시간 경로로 표현하지 않는다.

## 6. 반응형 프런트엔드

**React + TypeScript + Next.js + CSS Modules**를 사용한다. 실제 Tourism 저장소에 Next.js가 있으므로 그 구조를 활용한다. 세 화면은 React 컴포넌트로 구성하고 공통 상태를 공유한다. 단계 전환은 앱 상태로 관리한다. 내부 `/api/v1/day-trip` 요청은 Next.js의 경로 연결로 FastAPI에 전달한다.

React는 입력·선택·코스 상태에 따른 화면 갱신에 사용한다. 화면 크기에 맞는 반응형 배치는 CSS Grid, Flexbox, 미디어 쿼리로 구현한다. 기존 HTML 시안의 색과 카드 톤은 활용하고 고정된 휴대폰 프레임은 제거한다.

| 폭 | 배치 원칙 |
|---|---|
| 320~767px | 입력 지역·유형 한 열, 검색 버튼 전체 폭, 지역 바로가기 두 열·두 행, 장소 카드 한 열과 하단 주요 행동 |
| 768~1023px | 입력 지역·유형 두 열, 검색 버튼 오른쪽, 지역 바로가기 한 행, 장소 카드 두 열과 선택 목록 별도 행, 코스 목록·지도 두 열 |
| 1024px 이상 | 입력 지역·유형 두 열, 검색 버튼 오른쪽, 지역 바로가기 한 행, 장소 목록·선택 목록을 나란히 배치, 코스 목록·지도 두 열 |

초기 경계값은 구현 중 실제 콘텐츠에 맞춰 조정한다. 홈은 전체 폭의 검색 영역 안에서 필요한 입력만 보여주므로 조건 편집이 길어져도 옆에 빈 안내 열이 남지 않는다. 페이지 전체는 자연스럽게 세로 스크롤되며 카드 폭과 텍스트 길이 때문에 가로 스크롤이 생기지 않아야 한다. 초기 화면뿐 아니라 키워드를 펼친 상태, 긴 미지원 조건 안내, 사진 조회 결과까지 각 화면 폭에서 확인한다.

디자인은 밝은 중립 배경·짙은 본문·파란 주요 행동·청록 보조 강조로 정리한다. 원본 시안의 사진 중심 탐색과 사용자의 수정·선택 흐름은 유지한다. 장식 그림과 긴 소개를 제거하고 실제 검색·선택·이동 행동에 공간을 배정한다. 모바일에서는 선택 코스 진행과 다음 장소 길찾기를 하단 고정 영역에서 제공한다. 의미 없는 AI 점수, 과도한 온보딩, 제공하지 않는 메뉴는 배치하지 않는다.

## 7. 백엔드와 데이터 흐름

**React → FastAPI → TourAPI / LLM**

FastAPI는 입력 검증, 관광 검색 조건 변환, 외부 API 호출, 응답 정리, LLM 출력 검사와 실패 대응을 맡는다. 프런트는 조건 편집, 장소 선택, 순서 변경과 화면 상태를 맡는다.

관광 후보는 실제 API에서 조회하고, 상세정보와 최종 코스의 근거는 서버에서 확인한다. 브라우저가 보내는 장소 소개를 신뢰해 LLM 설명의 근거로 사용하지 않는다. 최종 코스의 장소 ID를 재조회해 강원도 범위·선택 조건·중복·존재 여부를 검사한다.

관광·LLM 비밀키는 서버 환경변수로 보관한다. 프런트 빌드에 들어가는 환경변수를 비밀키 저장소로 사용하지 않는다. 외부 요청에는 시간 제한과 요청량 제한을 두고, 사용자 오류 응답과 로그에 비밀키나 인증 URL을 포함하지 않는다.

개발·운영 중에는 Next.js의 경로 연결로 FastAPI와 연결한다. 프런트는 Next.js 빌드 후 운영 서버로 실행하고, 백엔드는 uvicorn으로 실행한다. 사용자가 접속하는 프런트 주소에서 내부 API를 요청한다. 프런트는 `web`, 백엔드는 `app` 디렉터리에 둔다.

첫 버전은 회원·공유·기기 간 동기화가 없으므로 영속 서버 DB를 필수로 두지 않는다. 코스 저장은 ID·순서·조건을 유지한다. 여행 시작일·직접 방문 체크·장소별 메모는 별도 브라우저 기록으로 저장하며 관광 원천 데이터를 대량 복제하지 않는다. 기록은 장소 ID 집합으로 구분해 순서를 바꿔도 유지하고 장소 구성이 다른 코스와 분리한다.

## 8. AI 구현과 평가

LLM 호출은 조건 해석과 최종 코스 설명에 집중한다. 설명은 여러 장소를 한 번에 요청할 수 있도록 설계한다. 카드 클릭과 순서 변경마다 LLM을 호출하지 않는다.

지역·기간·지원하는 분류 등 조회 가능한 조건과 ‘조용함’ 같은 주관적 선호를 구분한다. 지원하지 않는 조건은 사용자에게 알린다. 주차·무장애·반려동물 조건은 실제 데이터가 확보되지 않으면 충족을 보장하지 않는다.

LLM 응답은 정해진 형식과 길이를 검사한다. 거절·형식 오류·시간 초과 때도 실제 관광 정보와 직접 조건 선택을 사용할 수 있게 한다.

포트폴리오에서는 다음을 실제 결과로 설명한다.

- 예시 입력 10~15개에 대한 조건 추출의 성공·실패와 사용자 수정 반영 여부.
- 장소 ID의 존재·지역·중복 검증 결과.
- 근거 없는 문장이나 수치를 화면에 표시하지 않도록 처리한 방식.
- 관광 API 실패와 LLM 실패를 분리한 사용자 경험.
- 모바일·태블릿·PC에서 선택·교체·저장 흐름의 동작 확인.

이는 LLM 응용과 서비스 검증 경험이다. 자체 모델 학습이나 TensorFlow 개발 경험으로 표현하지 않는다.

## 원본 제안서와 이번 수정의 관계

원본 통합 제안서의 자연어 검색 → 공공데이터 확인 → 사용자 코스 편집 → 길찾기 → 저장·회고 방향을 유지한다. 사진 미션이나 수집 게임을 서비스의 중심으로 바꾸지 않는다. 이번 수정은 자동차 경로 조회와 코스 확인 뒤 행동을 연결하는 프런트·백엔드 개선이다.

현재 구간 연결은 카카오맵 외부 길찾기와 카카오모빌리티 자동차 경로 조회를 함께 제공한다. 관광 장소를 재검증한 뒤 조회한 예상 시간·거리·도로 경로를 표시한다. 자동차 기준 조회 시점의 예상값이며 첫 장소까지의 이동·체류·주차 시간은 제외한다. 전체 하루 일정의 실현 가능성이나 최적 방문 순서를 보장하지 않는다. 체류 시간 기반 일정 검증은 다음 단계다. 목적형 데이터의 자동 조건 판정·벡터 검색·MCP·공유·사진 회고는 구현 상태에 맞춰 단계적으로 추가한다.
