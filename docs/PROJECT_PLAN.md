# StoryRoute 프로젝트 계획

2026년 10월 17일 코드·문서 점검 기준. 운영 화면을 확인한 날짜와 자동 테스트 결과는 [검증 기록](VALIDATION.md)에 따로 적는다.

## 서비스와 해결할 문제

StoryRoute는 강원특별자치도의 실제 관광지를 찾고 1~3곳의 당일 코스를 만드는 반응형 웹 서비스다. 장소 검색부터 비교, 방문 순서 확인, 길찾기, 현장 기록까지 여러 화면을 오가는 부담을 줄이는 것이 목적이다. 프런트와 백엔드를 한 프로젝트에서 개발한다.

검색 결과를 자동으로 정답처럼 정해 주기보다 사용자가 조건과 장소를 직접 고칠 수 있게 한다. 장소의 이름·주소·유형은 한국관광공사 데이터로 확인하고, AI는 문장 조건 정리와 공식 소개문 속 근거 선택에만 사용한다. API에 등록됐다는 사실이 현재 영업이나 현장 상황까지 보장하지는 않는다.

## 현재 제공 범위

| 기능 | 현재 동작 | 경계 |
|---|---|---|
| 지역 탐색 | 강원도 전체 또는 18개 시·군 선택 | 전국·현재 위치 반경 검색은 미구현 |
| 문장 탐색 | 기본 규칙으로 조건 정리, 선택 시 AI 해석 | 해석 결과를 사용자가 수정하며 모든 희망 조건 충족을 보장하지 않음 |
| 관광사진 탐색 | 촬영 지역을 확인한 사진에서 해당 지역의 장소 검색으로 연결 | 사용자 사진 업로드·이미지 인식 아님 |
| 장소 비교 | 사진 넘기기·확대, 소개·운영정보, 오디·연관·편의정보 | 제공된 정보만 표시, 부가 자료 없음과 조회 실패 구분 |
| 코스 구성 | 1~3곳 선택·교체·순서 편집, 서버에서 장소 재조회 | 경로 최적화·자동 일정 추천 아님 |
| 자동차 이동 | 현재 방문 순서의 인접 구간 예상 시간·거리·도로 경로 | 첫 장소까지의 이동·체류·주차 시간 제외 |
| 시간 계획 | 첫 도착 시각·체류 시간과 확인된 이동 구간으로 시각 계산 | 영업시간·방문 가능성 판정 없음, 입력값은 저장 코스에 포함하지 않음 |
| 여행 기록 | 직접 방문 체크·장소별 최대 500자 메모 | 브라우저 저장, GPS 인증·계정 동기화 아님 |
| 계정 코스 | 카카오 로그인 후 코스 생성·목록·재열기·삭제 | 최근 20개 목록, 서버 중복 저장 방지·수정 API·공유는 미구현 |

## 대표 사용자 흐름

1. 지도에서 시·군과 장소 유형을 고르거나 문장·관광사진으로 탐색을 시작한다.
2. 문장을 입력했다면 정리된 지역·유형을 확인하고 수정한다. AI 전송 선택은 기본 해제이며 선택하지 않아도 조건 정리와 검색을 이용한다.
3. 실제 조회 결과의 사진·주소·상세 정보를 비교하고 최대 세 장소를 담는다. 한두 장소로도 코스를 만든다.
4. 서버가 선택 ID의 장소·지역·유형을 확인한 뒤 코스를 반환한다. AI 근거는 선택된 경우에도 원문 대조를 통과해야 표시한다.
5. 방문 순서를 정하고 자동차 이동을 조회한다. 순서를 바꾸면 이전 경로는 숨기고 다시 확인한다.
6. 여행을 시작해 다음 장소 길찾기를 열고 방문 체크·메모를 남긴다. 회원은 코스를 계정에도 저장할 수 있다.

화면별 동작과 실패 시나리오는 [사용자 시나리오](MVP_USER_SCENARIO.md), 상태와 요청 형식은 [프런트·API 명세](FRONTEND_API_SPEC.md)를 따른다.

## 설계 원칙

- 실제 관광 장소와 AI 출력을 구분한다. 외부 API에 없는 주소·좌표·영업시간을 만들어 넣지 않는다.
- 문장·사진·지도 중 하나의 입력 방식만 펼치고, 입력 방식 변경만으로 이전 조건을 지우지 않는다.
- 지역 선택만으로 강제 스크롤하지 않는다. 다음 행동과 저장 결과가 모바일에서도 분명하게 보이게 한다.
- 사진·오디·연관·편의정보는 필요할 때 조회한다. 부가 자료 실패가 기본 장소 소개를 막지 않게 한다.
- 브라우저 저장과 계정 저장을 구분한다. 순서만 바뀐 코스의 방문 기록은 유지하고, 장소 구성이 달라지면 다른 기록으로 관리한다.
- 원본 관광 데이터를 계정 DB에 복제하지 않는다. 저장 코스는 ID·순서·조건을 보관하고 다시 열 때 현재 정보를 조회한다.

색상·여백·지도 표현은 [디자인 기준](DESIGN.md), 요청 경로와 배포 구성은 [시스템 구조](SYSTEM_ARCHITECTURE.md), DB와 ERD는 [데이터베이스 구조](DATABASE_SCHEMA.md)에 모아 관리한다.

## 먼저 보완할 부분

| 우선순위 | 현재 한계 | 완료를 판단할 기준 |
|---|---|---|
| 1 | 계정 저장 API는 장소 ID 형식·유형을 검사하지만 실제 관광지를 다시 조회하지 않음 | 직접 API를 호출해도 잘못된 장소·지역·유형은 저장 전에 거절 |
| 2 | 계정 목록은 최근 20개이며 코스별 추가 쿼리 발생 | 페이지 이동·쿼리 수·인덱스를 검증하고 목록 수에 비례한 쿼리 증가 제거 |
| 3 | 서버 중복 저장 방지·인증 및 계정 API별 요청 제한 없음 | 반복 저장·동시 요청·재시도 정책과 실패 응답을 테스트 |
| 4 | 지연·오류율 계측과 PR 자동 검사 부족 | 외부 서비스별 지연과 실패를 분리해 보고, 비밀키 없는 검사를 PR에서 실행 |
| 5 | 복구본 보관기간·다른 실제 기기에서의 복원 등 미확인 | 운영 설정 또는 실제 수행 결과를 날짜와 함께 기록 |

현재는 프로세스별 호출량 제한과 캐시를 사용한다. 인스턴스를 늘릴 때는 전체 요청량이 합산되지 않는 문제부터 해결한다. 서버 유휴 해제, 외부 관광 API, 사진 다운로드의 지연은 나눠서 측정한다. 이 항목들은 개선 계획이며 구현 완료를 뜻하지 않는다.

## 확장 판단

방문 기록의 계정 동기화는 사용자 필요와 저장·충돌·삭제 정책부터 정한다. 공개 코스 공유, 사용자 사진·리뷰, 전국 확장, 의미 검색, 운영시간을 반영한 일정 검증은 현재 범위에 없다. 사용하는 문제와 검증 방법이 분명해졌을 때 추가한다.

공모전 제출 순서와 지난 접수 일정은 개발 기획에서 제외했다. 이전 제안과 작업 이력은 Git 기록으로 확인한다.
